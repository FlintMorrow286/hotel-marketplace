# Hotel Marketplace — B2B2C платформа бронирования жилья

**Статус:** проектирование + подготовка к Phase 1
**Дата:** 2026-09-24

> **Что это:** маркетплейс, где партнёры (отели, хозяева квартир, апартаментов, комнат)
> размещают свои объекты, а гости бронируют и оплачивают **на нашем сайте**.
> Мы берём комиссию с подтверждённой брони.
>
> **Главная задача сейчас:** построить **ядро бронирования** — систему, которая
> гарантированно не создаёт double booking. Без неё всё остальное не имеет смысла.

## 🎯 Продукт одним абзацем

Партнёр заводит объект в нашем личном кабинете и ведёт календарь **у нас**.
Гость ищет жильё в каталоге, бронирует и платит **у нас** (instant book, 100% предоплата).
Бронь подтверждается автоматически после оплаты; партнёр получает уведомление в Telegram/email.
Мы берём комиссию. Внешние площадки (Avito, Суточно.ру, Яндекс Путешествия, Airbnb) —
это **каналы**, которые подключаются позже (Phase 2+): мы в них экспортируем занятость
и импортируем брони, но **главный календарь всегда наш**.

### Ключевые решения (подробнее в ARCHITECTURE.md §10)

| Параметр | Решение |
|---|---|
| Типы объектов | любые жилые помещения (квартиры, апарты, комнаты, дома, номера) |
| Instant booking | **да** — подтверждение автоматически после оплаты |
| Предоплата | **100%** при бронировании |
| География старта | **Крым** (Ялта, Севастополь, Симферополь, Алушта, Судак, Феодосия, Евпатория, Саки, Керчь) |
| Корзина (multi-room) | нет в Phase 1 — одна броня = один объект/тип номера |
| Отмена | бесплатно до 24:00 предыдущего дня, дальше — штраф по тарифу |
| Монетизация | комиссия с подтверждённой брони |

## 🛠 Технологический стек

> Финальное решение — **Python**, не Go. Узкое место ядра — блокировки строк в Postgres,
> а не язык; плюс команда знает Python, а Go — нет. Go остаётся опцией на далёкое будущее
> **только для sync worker** (ADR-010).

**Бэкенд:**
- Python 3.12, FastAPI, Uvicorn, asyncio
- PostgreSQL + **asyncpg** (основной драйвер) + psycopg 3 (sync-задачи)
- **БЕЗ ORM — чистый SQL.** Блокировки `FOR UPDATE` и изоляция `SERIALIZABLE` должны быть
  видны в коде явно (ORM их прячет и ломает)
- Миграции — **ручные `.sql` файлы** по порядку (без Alembic)
- Redis (`redis.asyncio`) — кэш доступности, очередь outbox
- Pydantic v2 — только валидация на границе API
- JWT-авторизация (scopes: guest / partner / admin)
- aiogram 3 — Telegram-бот партнёра
- httpx — вызовы каналов (Phase 2+), sentry-sdk — наблюдаемость

**Фронтенд:** React 18 + TypeScript + Vite + Tailwind CSS 4, react-router-dom, TanStack Query,
WebSocket (FastAPI) для live-обновления шахматки.

**Инфра:** self-hosted, Docker Compose (postgres 16, redis 7, api, web).

**Платёж — заглушка.** `PAYMENT_MODE=stub` — имитация успешной оплаты для разработки ядра
(мгновенный `confirmed`). Реальный эквайринг — отдельная реализация интерфейса
`PaymentProvider`, подключается после решения юридических вопросов. **Ядро бронирования
не зависит от того, какой режим включён.**

## 🔒 Главное: как мы избегаем double booking

1. **Source of truth — наша PostgreSQL.** Все брони идут через одну точку.
2. **Атомарный hold:** `SELECT ... FOR UPDATE` по диапазону дат с сортировкой ключа
   (без дедлоков) → декремент allotment → `hold` на 15 минут.
3. **Idempotency-Key** на каждом `POST /bookings/hold` — дублирующий запрос не создаёт дубль.
4. **Hold TTL + reaper job** — не оплатил за 15 мин → инвентарь вернулся.
5. **Transactional outbox** — данные в каналы уходят уже *после* коммита, ретраи с backoff + DLQ.
6. **Reconciliation cron** (Phase 2+) — сверка нашей занятости со срезом канала.

Синхронизация с каналами **не может** сама по себе предотвратить double booking
(у неё всегда latency > 0), поэтому окно продаж должно быть одно — наша БД.

**Definition of Done Phase 1:** гость находит объект в Крыму → бронирует → оплачивает 100%
(через stub) → видит подтверждённую бронь; партнёр видит её в шахматке и получает
уведомление; в админке — комиссия по сделке.

## ✅ Критерии успеха ядра (к концу 2-й недели)

- `POST /bookings/hold` работает с p95 < 300 мс
- **Ноль double booking** во всех тестах, включая гонки
- 100 конкурентных запросов на 1 свободный номер → ровно 1 success, 99 conflict
- Цепочка `hold → pay(stub) → confirmed` работает через curl от начала до конца

Как это проверить (всё воспроизводимо командами):

```bash
bash scripts/dev_services.sh                         # Postgres + Redis, если не подняты
uv run pytest tests -q                               # бэкенд: БД создаётся и удаляется самим набором
uv run ruff check app tests scripts
cd web && npm ci && npm test && npm run typecheck   # vitest + типы
# нагрузка на горячий путь (сервер уже запущен на APP_PORT):
uv run python scripts/load_holds.py --n 100 --units 1     # 1 x 201, 99 x 409
uv run python scripts/load_holds.py --n 100 --units 100   # 100 x 201 на одних и тех же строках
# e2e гостевого пути в браузере: web/playwright.config.ts, `npm run e2e` (см. job `e2e` в CI)
```

`scripts/load_holds.py` сам создаёт и убирает тестовый номер и завершается с кодом 1,
если база расходится с ответами API или кто-то получил не 201/409.
Холды на один тип номера выстраиваются в очередь (`app/db/tx.py`: `unit_queue`), поэтому
шторм на одни и те же строки не даёт 503.

## Run with Docker

Скопируйте .env.example в .env, задайте сгенерированные значения для JWT_SECRET, WEBHOOK_SEAL_KEY и POSTGRES_PASSWORD, затем запустите docker compose up --build -d. Настройки прокси и резервного копирования описаны в docs/DEPLOY.md.

## Dev services without Docker

Запустите bash scripts/dev_services.sh: скрипт поднимет локальные PostgreSQL и Redis и создаст роль/базу из DATABASE_URL. Затем запустите API командой uv run uvicorn app.main:app --reload --port 8002, а фронтенд отдельно из каталога web/ командой npm run dev.
